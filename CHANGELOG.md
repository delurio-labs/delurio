# Changelog

While the version is 0.x, a release that can judge the same graphs differently (a new check, a stricter schema) bumps the minor; a fix that judges nothing differently bumps the patch.

## 0.14.0 (unreleased)

- New rule of `check`, which fails `--strict`: `event-unhandled`, a node that sends an event (`emits`) in a state that shows it enabled and does not handle that event (SPEC.md §4), the part of [#3](https://github.com/delurio-labs/delurio/issues/3) that asks for events handled where they are shown. In every situation the checker reaches, a state that shows the node (`in`, `unless`, and its `when` over that situation's context) and does not disable it (`disabledIn`, `disabledWhen`) has a transition on the event in its `on`. Three are not held, by what SPEC.md §2 says of them: a node that sends `NAVIGATE`, the person leaving the page, which is always possible; an exit, which has no transitions, so what a node on its page does is outside the flow; and a state with `always`, which the flow passes at once. It is given once per node and state, at the node in `ui.yaml`; where the node's `when` or `disabledWhen` decides it, its notes, and in SARIF its code flow, give the way from a start to the first situation that shows it enabled. It reads the exploration `check` already makes, so no flow is explored twice. Before, a Save button left enabled while its step runs, an answer that a question's saving state does not handle, and a link back to the list shown in states that do not handle it all passed `--strict`; Medaris's graphs had all three. On delurio's own graphs it finds 24, each in a state that runs a server step. A graph whose screens leave no event unhandled is judged as before; a project can record what it finds with `--baseline` while it fixes it.
- `renderCheckScreens` in `@delurio/cli/wireframe` gives each expectation's `native` again: 0.13.0's JavaScript module dropped the kind the addon returns, so a replay or `kit check` built on the module could not find a `native` control among the controls of its kind. The command line was not affected.
- A node may say how it looks in a state: `tone`, one of `neutral`, `info`, `success`, `warning` and `danger`, or a map from these to expressions over the context, of which the first that holds wins, such as an exam's countdown that turns red in its last five minutes (`tone: { danger: "clock == 'lastFive'" }`, SPEC.md §4). It is how the node looks, never all it says (WCAG 2.2, 1.4.1): its words and its role say the same, and the accessibility tree, `kit check` and a replay are as they were. An expression of a `tone` that does not parse, or names what is not a variable, a guard or `state`, keeps the graph from loading, as `checked` does; a word that is not a tone is the `schema` rule's. The page draws a fixed tone and names it in the node's annotations, and names a map there as `tone danger when …`, as it names `when`; the fixed components draw a tone as the class `wf-tone-<word>`, red for `danger`, with styles the page adds only when a node of its flow has a tone (`TONE_CSS` in `@delurio/cli/wireframe`, for a video stage too). `renderStageScreen` takes the situation's context as its sixth argument and draws each node in the first tone of its map that holds there; without it, in its fixed tone only. Graphs without `tone` are drawn byte for byte as before.
- A kit draws a node's tone with the slot `{tone}` and `tones`, a map from each tone to the word the slot gives, with `default` for a node without one, at the top of kit.yaml and in a component, whose own is read first (SPEC.md §8). A kit that has `tones` gives an entry for every tone a node drawn with a `{tone}` template may take, any of a map included: one it lacks is `kit-uncovered`, as an intent is. A key of `tones` that is not a tone keeps the kit from loading.
- A kit may carry its fonts: `fonts`, a list of `{ family, file, weight, style, unicodeRange }`, each `file` a woff2, woff, ttf or otf file in the kit's folder, licensed for embedding (SPEC.md §8). The page and the video stage's CSS (`kitCss`) embed each as a data: URL in an `@font-face`, once per page, so a kit still fetches nothing and its screens are drawn in its own fonts on any machine. A file may be at most 2 MiB, and a kit's files at most 8 MiB together, room for four variable fonts of about 1.5 MB. New rule of `check`, which fails `--strict`: `kit-font`, at a font entry whose file is not in the kit's folder (an absolute path, `..`, or a link out of it, none of which is read), is not there, is not a file, is not by its first bytes the format its name says, or is too large; it is given once per kit, and `page` warns of it and draws without the font. New warning of `check`, which fails nothing: `kit-font-unembedded`, a family the kit's CSS draws in first (the first of a `font-family` or `font` stack, through the custom properties it reads from the tokens or the CSS) that is neither a family of `fonts` nor a generic one, where the tokens or the CSS write it. `kitFamilies(kit)` in `@delurio/cli/kit` lists the families a kit carries, so that a tool that draws the screens in a browser can ask whether it drew them. Kits without `fonts` are drawn as before, and the example kit leads with `system-ui`, so it is warned of nothing.
- A repeat's items may be given as rows (SPEC.md §4): `samples: { question.options: [ { id: a, text: "Four" }, { id: b, text: "Three" } ] }`, a list of maps under the repeat's data. A node with that `repeat` is then drawn once per row, on the page, on the tutorial stage and in `kit check`'s screens, which expect each element it draws with its `index`; a param that reads `row.<field>` (`params: { option: row.text }`) takes that row's field, and `nodeTexts` gives the texts of every row. A repeat node's `checked` may read its row (`checked: "row.id == answer"`), so the options of a radio group are written as one node again; `row.<field>` on a node without `repeat` keeps the graph from loading, as before. Without rows, a node is drawn once, as before. Before, Medaris's exam showed one option per question and could not draw the one chosen.
- `renderStageScreen(g, state, reveal, warn, kit, ctx)` in `@delurio/cli/wireframe` takes the context of the situation the stage shows, a map of the flow's variables to their values: each node's `checked` is read over it, for each row it is drawn for. Without it, or with `null`, only `checked: true` is drawn, as before; the page draws each state's screen once, for all the situations that show it, so it draws only that.
- An effect may set a variable from the row that was pressed, `set: { answer: row.id }`, on a transition whose event a repeat node sends (SPEC.md §4). The flow does not say which row is pressed, and the sample rows only illustrate the screens, so the checker lets such a variable take any of its values, as `havoc` does, whether rows are given or not. Before, `row.id` was set as the text it is.
- A tutorial's press says which row of a repeat node it presses, `{ press: option, row: 2 }`, counted from 1 (SPEC.md §7): the step takes the case in which every variable the transition sets from the row has that row's value. `check` gives `tutorial-mismatch` at a `row` that is not a whole number from 1, on a step that presses nothing or a node without `repeat`, past the rows the samples give, of a row without a field the effects read, and where no case of the press has the row's value. A press without `row` takes the first case, as before.
- Rows and tables in the wireframe (SPEC.md §4): adjacent nodes that share a `repeat` are drawn side by side, one row per item, on the page, on the stage and in `kit check`'s screens; a List holds those rows as its items, and a ListItem that begins a row holds the nodes beside it. A List whose role is `table` or `grid` draws its header cells (role `columnheader`) as its header row and its repeat nodes as its rows. With a kit each node keeps its template inside the rows, a table's row being an element of role `row`; the expected accessibility tree and `kit check`'s expectations follow the rows. Before, a table was drawn as one column, and the number and the state of one question in a list stood on separate lines. Screens without a table and with no nodes that share a repeat are drawn as before.
- The ui schema lets a sample be a list of rows, each a map of strings, numbers and booleans, with at least one row.
- A node's `when` that does not parse, or names what is not a variable, a guard or `state`, keeps the graph from loading (exit 1), at the `when` in `ui.yaml`, as a `checked` or a `disabledWhen` does (SPEC.md §4); decided on 22 Nov 2026. Before, such a `when` was passed over without a word: the page drew the node, `event-unhandled` decided nothing for it, and only a replay or a tutorial that read it stopped. It stops none of delurio's own graphs, whose nodes give 835 `when`s, nor of Medaris's, which give 3,954.
- A node may stay usable while a step runs: `duringStep: true` on it (SPEC.md §4) says that in a state that runs a step (`invoke`) the node may be pressed, and that its event is handled once the step ends, by the state the step's outcome leads to; decided on 22 Nov 2026. `event-unhandled` then does not hold the step's state to the event, but every situation that the step's `DONE` and `FAIL.<class>` lead to, past states with `always`, from each situation of the step that shows the node enabled: it handles the event, shows the node disabled or not at all, is an exit, or runs a step of its own that shows the node enabled, where the press waits again, onward, each situation walked once so that a cycle of steps ends. Where one does none of these, the error is given for the step's state, as before, and says the outcome and the state the press is left in; its notes, and in SARIF its code flow, give the way there through the step. The error for a node shown enabled in a step's state now says the marker too. A replay does not press a node while a step runs, so it is not changed. New warning of `check`, which does not fail `--strict`: `during-step-unused`, a node marked so where no state that runs a step shows it enabled (by `in`, `unless` and `disabledIn`), or that sends `NAVIGATE`; the `schema` rule refuses the marker on a node that sends no event. A graph without the marker is judged as before. Of the findings in a step's state, the marker would clear all 24 on delurio's own graphs and 725 of 945 on Medaris's, those whose step's outcomes already handle the event, disable the node or do not show it; Medaris's other 220 lead, mostly through a `FAIL.<class>`, to a state that shows the node enabled and does not handle it.

## 0.13.0 (2026-11-21)

- A variant of a flow's binding written beside it, `binding.<variant>.yaml` (`binding.noSessions.yaml`, `binding.common.yaml`), is a binding (SPEC.md §7): `check` holds it to the binding schema, as it holds `binding.yaml` and a shared `<name>.binding.yaml`. Before, it was read as no graph file at all, and a value the schema refuses passed unseen; Medaris had 271 such files.
- A locator's `nth` may be negative, counting from the end: -1 is the last of what the rest finds, such as the row a step has just added (SPEC.md §7). The schema refused it, though a replay hands `nth` to the browser's locator as it is.
- A field or an action that is an HTML control WAI-ARIA gives no role, an `<input>` of type `date`, `time`, `datetime-local`, `month`, `week`, `file` or `color`, or a `<summary>`, says which with `native` instead of a `role` (SPEC.md §4). `role-missing` does not apply to it; a `role` beside it, or `native` on a node that is no field or action, is refused by the `schema` rule. `kit check`'s expectations carry it (`native`), so a replay can find the control by its name among controls of that kind.
- New command: `delurio affected --base <ref> [--head <ref>] [--graphs <dir>] [--repo <checkout>] [--json] [--all]` says which graphs a change touches, each with why, and which changed files touch none, so that a repository's CI checks or replays only the flows a pull request touches (SPEC.md §9). The change runs from the merge base of `--base` and `--head` to `--head`, or to the working tree with the files git does not ignore. A graph is touched by its own files; by a `source:` anchor, line-precise where the anchor names a line and the change's lines are known, file-level otherwise; by an action of its domain that the change adds, removes or changes, or that a changed entity, policy or invariant names; by a binding anywhere in the repository, one it extends, a file it uses, or a graph it enters through; and by a catalog or a kit it shares. What cannot be known touches every graph and says why: no merge base, a list of changed files cut short, a graph file that does not load, a file of the graphs folder that belongs to no graph. `--json` writes `delurio-affected/0`. It is the selection delurio's replay makes, without two rules that are only delurio's own repository's (its citation forms in code comments, and its engine's own files): on the 25 latest merges of that repository and on every case of its tests, it gives the same answer byte for byte once those two rules are set aside. One difference: an added line that begins with `++ ` is a line of the patch, not the header of another file, so the hunks after it are still the file's. `delurio_core::affected` is the selection alone, over the changed paths (with their lines, when known) and each side's files, for a program that has a repository's texts and no checkout. It judges no graph differently: `check`, `page` and `diff` are as they were.

## 0.12.0 (2026-11-21)

- A node of a flow's screens may say which field of the flow's domain it holds: `holds: <Entity>.<field>`, the value a text shows or a field takes (SPEC.md §4). New rule of `check`, which fails `--strict`: `holds-unknown`, at a `holds` that names an entity the domain does not have, a field the entity does not have, or a domain that is not found beside the flow; an entity that gives no `fields` yet is not held to them. A `holds` that is not `<Entity>.<field>` is the `schema` rule's. Graphs without `holds` are judged as before.
- What a recording masks (SPEC.md §7): a recording, a video made from it and a replay's screenshots blur every element of a node that holds a field whose `sensitivity` the binding's `mask` names, in every frame of a state that shows it. What is masked is the binding's to say: `mask` lists the sensitivities, `[credential]` when it is left out; `mask: [credential, personal]` also keeps people's names and addresses out of a recording made on real data, and `mask: []` masks nothing, for a tutorial filmed with a password made up for it. `maskedNodes(g, mask)` in `@delurio/cli/graph` names those nodes, in the order of `nodes`, the domain looked up beside the graph as `check` finds it; `UiNode` gives `holds`.
- A schema for bindings (SPEC.md §7): `schemas/binding.schema.json`, every key a replay reads of a flow's binding and of a navigation graph's. `check` holds `binding.yaml` and a shared `<name>.binding.yaml` to it, under the rule `schema`, which fails `--strict`: a key that is not one (a misspelt `scenarios`, or `exact` on a locator, which a replay passed over in silence), a value of the wrong kind, an action with two verbs or none, `expect` without `run`, a state's `fail` without its `call`, a `setup` that does more than run commands. A binding is YAML without anchors, aliases or tags, as every graph file is (SPEC.md §1). Before, a mistake in a binding showed only when a replay ran it, which needs a browser and the app (the Omnitron pilot, 21 Nov 2026). What a binding names in the graph is still held by the replay, which loads it with no browser under `replay --check`. A project whose bindings give a key the schema does not know can record the findings with `--baseline`.

## 0.11.0 (2026-11-16)

- The checker is written in Rust: `check`, `page` and `diff`, and every module the package exports, are the TypeScript checker's ported one module at a time (crates/delurio-core, crates/delurio-page, the `delurio` binary in crates/delurio, and the addon in crates/delurio-node). It judges every graph as 0.10.0 does: on the examples, on delurio's, QAuth's and Medaris's own graphs, and in the 35 behaviour cases of the CI, every finding (its rule, level, file, line, words and fingerprint), the SARIF, the exit codes, every page, diagram and Mermaid file, and every diff are those 0.10.0 gives. Where 0.10.0 stopped with a JavaScript TypeError on a value of the wrong type, 0.11.0 reads the value as absent (the `schema` rule already reports it), and a baseline or a file it cannot read is an `error:` line, not a stack trace.
- It reads YAML as 0.10.0 did: the yaml library 2.9.1's lexer, parser and composer are ported, so a refusal (SPEC.md §1), a YAML error and a key are found at the same place and in the same words. The `schema` rule gives Ajv 8.20's findings: Ajv's evaluation of the keywords the schemas use is reproduced. A flow's diagram is still laid out by elkjs 0.12.1 itself, now run inside the binary (QuickJS-NG), so its places are the same to the last digit as before and as the dashboard's.
- Faster and smaller: on Medaris's 179 graphs, `check --strict --baseline` takes 34 s and 299 MB, where 0.10.0 took 87 s and 1 GB; `page` takes 96 s, where 0.10.0 took 15 minutes. On delurio's own graphs `check` takes 56 s and 0.56 GB, where 0.10.0 took 228 s and 4.2 GB (more than Node's default heap): the explorer keeps each (state, context) pair as packed words, 16 bytes a pair, so delurio's billing.plan (16.76 million pairs) explores in 21 s and 0.54 GB.
- One new limit: a context variable may hold up to 65,536 values.
- For installers: `delurio` is one static binary, from the GitHub release of each tag (Linux x64 and arm64, glibc and musl, macOS arm64, Windows x64, with SHA256SUMS), from `cargo install --locked --git https://github.com/delurio-labs/delurio --tag v0.11.0 delurio`, and in the image `ghcr.io/delurio-labs/delurio`, which is now the binary alone `FROM scratch`. `npm install @delurio/cli` installs the same command (`npx delurio`) and the same entry points with their types, on a prebuilt addon of the platform: npm picks one of six packages `@delurio/cli-<platform>` (no install script). The package needs Node 26 or later and depends only on elkjs. A process that loads the library under Node's permission model needs `--allow-addons`, and a bundler must leave `@delurio/cli` external.
- The library: `renderPage` and `callLine` (`@delurio/cli/html`) are gone; `delurio page` writes a flow's page. An `Exploration` must come from `explore`, and a graph, a navigation graph or a kit is read once per object (a copy is read again).

## 0.10.0 (2026-11-16)

- New warning of `check`, which fails nothing: `role-missing`, a node of type `field` or `action` that gives no `role` (SPEC.md §4). A screen reader, a replay and `kit check` find a control by its WAI-ARIA role; before, `kit check` expected such a node's type (`field`, `action`) as its role, which no drawn element can have, so every such node was a mismatch. `@delurio/cli/wireframe`'s `Expectation` says so with `roleGiven`, so a kit check holds that node's name and state only.
- A kit's CSS may say `scroll-behavior` and `overscroll-behavior`. The check of script-like CSS took any `behavior:` for old Internet Explorer's script binding, so a kit made from a product's own CSS was refused for scrolling smoothly. `behavior:` itself is still refused.
- New rule of `check`, which fails `--strict` (SPEC.md §9): `source-unresolved`, a `source:` anchor whose file is not there, is a folder, or whose line is 0 or past the file's end, at the anchor. Every anchor is held, in a flow, its screens, a navigation graph and a domain: each `source` that the file's schema gives as an anchor (`sourceAnchor`), so a key `source` that means something else (a nav graph's own `source`, a sample value or a parameter of `ui.yaml`, a field of a record) is none. The path is read from the application's repository root, `--app` or the folder `check` runs in, as a need's evidence is; an anchor of a navigation graph too, and where the path is there under its `source.app` the finding says so. Before, only a need's evidence was resolved: of Medaris's 18,843 anchors, the 125 of its navigation pages written from the app folder (`app/page.tsx`) passed, and so did 34 of QAuth's 556 that are past their file's end. A project whose graphs give such anchors can record them with `--baseline`: they are then printed as warnings until they are fixed, and a new one fails.
- New rule of `check`, a warning, which fails nothing (SPEC.md §9): `citation-unresolved`, a `path:line` in a graph's words (a `description`, a `say`, a `note`, a `rule`, a need's `missing`) whose file is not there or whose line, or a range's last line, is past its end. Only a token that reads as a path from the repository's root is looked at: a folder of the root first, a file with an extension last. Sample values, an entity's records and a need's evidence are not words.
- A need's `source` evidence is resolved as an anchor is: a folder is now said to be a folder, and a line 0 does not resolve.
- `check --no-app` checks a project's graphs without its code (SPEC.md §10), as the panel checks a graphs folder alone: the anchors, the citations in words, and a need's `source`, `test`, `setting` and a `scenario` whose binding is named by its path are not looked for, and the output says once how many were not, on a line before the summary (`delurio check: note: --no-app: …`) and as a notification of the run at the level `note` in SARIF (`invocations[0].toolExecutionNotifications`). A need's `state` and `node`, a scenario of the flow's own `binding.yaml` and every other rule are checked as before. `--app` and `--no-app` together are refused (exit 1). Before, such a check gave an `evidence-unresolved` error for every path.
- SPEC.md §13: a missing need's `state` and `node` name only what is not built yet, as a replay leaves out every state and node that only missing needs name; a gap that is about something built names it in its `need` or `note`. New rule of `check`, a warning: `need-names-built`, at a missing need's `state` that names a state of a captured flow that names its code. Medaris's captured graphs had named 110 built states so, before they were moved to notes. A state of a captured flow that only missing needs name is not built, and `source-missing` no longer asks it for a `source` (SPEC.md §9).
- An entity may carry `note` (SPEC.md §5), as an action, a refusal and an invariant do. Before, the `schema` rule refused it.
- Decided on 16 Nov 2026 (SPEC.md §5): an entity or an action written before its code says `planned: <why>`, which a captured domain, whose `status` is given once, could not say of its parts. New rule of `check`, which fails `--strict`: `planned-built`, at the `planned` of an entity or an action that also names its code, with a note where its `source` is. Graphs without `planned` are judged as before.
- SPEC.md §1: a tool that reads or writes graph files with a YAML 1.1 library, such as PyYAML, reads `on`, `off`, `yes` and `no` as booleans, where the CLI reads YAML 1.2 strings: quote such a name, or read YAML 1.2.
- The toolchain is current: Node 26 (`engines.node` `>=26`, CI and the release on Node 26, the image on `node:26.13.1-alpine3.24` pinned by its digest), `@types/node` 26.6.6, elkjs 0.12.1, npm 12.2.2 for the staged release, docker/login-action 4.8.0 and sigstore/cosign-installer 4.1.3, each pinned by its commit. TypeScript 7.0.2, ajv 8.20.0, ajv-formats 3.0.1 and yaml 2.9.1 are already the newest stable releases more than 7 days old. The examples give the same findings, SARIF and pages as on Node 22 with elkjs 0.12.0. A project that runs the CLI on Node 22 or 24 is warned by npm that it wants 26.
- The examples give the same findings as before: none.

## 0.9.0 (2026-11-16)

- `check` parses each file once however many graphs read it. Before, it parsed a flow's domain again for every flow that names it, and every flow again for every flow that starts another: on delurio's own 41 flows it took 12.7 s, of which more than half was parsing the same files again; it now takes 5.8 s. It judges nothing differently: the same graphs give the same findings, in text and in SARIF, as 0.8.0 gives.
- A graph that cannot be loaded is reported, and the other graphs are still checked. Before, a `ui.yaml` with no `catalog` stopped the whole check with a stack trace (`ERR_INVALID_ARG_TYPE`), and so did a catalog file that was not there (`ENOENT`), a catalog that was not JSON, a `flow.yaml` or `ui.yaml` that was not a map, a flow with no `states`, a state that was not a map, and a guard, an assertion or a `starts` value that did not parse. Each is now a `load` error (exit 1), in text and in SARIF. A `ui.yaml` with no `samples` or no `nodes` now loads (the `schema` rule still reports a missing `nodes`); before, one whose words had a placeholder stopped the check the same way.
- A `load` error is given at its place (SPEC.md §10): the file it is in and the line of what it is about, or the line and column a parser gave. Before, every load error but a YAML one was given at `flow.yaml:1:1`, and a YAML error of `ui.yaml` at its line but in `flow.yaml`. Now a transition to a state that does not exist is given at the transition; a node's unknown state at that item of its `in`, `unless` or `disabledIn`; an unknown `focus` state, a `checked` that cannot be read and a kit that cannot be read at their keys in `ui.yaml`; a missing or unreadable catalog at `catalog`; a catalog that is not JSON in the catalog, at the place the parser gave; a guard that does not parse, or names what is not a variable or a guard, at the transition that uses it (a named guard at its own line); an unknown effect at its transition; a non-exhaustive `always` at its `always`; an assertion at its `never`. Their messages and fingerprints are unchanged, so a baseline still knows them.
- A started flow is looked up among the graphs beside a flow without reading one that cannot be read: before, a neighbour's YAML error was also reported as a `load` error of every flow that starts another one.
- `--baseline`: a known error that keeps a graph from loading is printed as `error`, since it fails the run (exit 1) however often it was seen. Before, it was printed as `warning` while the run failed and the last line counted it as an error. The last line now counts each finding at the level it is printed at, so a known error printed as `warning` is counted as a warning. Exit codes are unchanged.
- New rules of `check`, which fail `--strict` (SPEC.md §2): `state-unreachable`, a state that no situation the flow starts in reaches, which the page already marked; and `state-no-way-out`, a state that is not an exit (`type: final`) and has no `on`, `always` or `invoke`, so that a flow that reaches it stops there without ending. Both are given at the state. Before, `initial: cart`, `cart: { on: { CONTINUE: done } }`, `pay: { by: human }` and `done: { type: final }` gave no error at all; now `pay` gives both. Transitions that no situation takes still fail nothing (#2).
- `catalog-key-missing` holds the catalog of every locale in `locales` (SPEC.md §4), at the key in `ui.yaml`, and a locale whose catalog file is not there is one error at `locales`. Before, only the catalog `ui.yaml` names was read, and a key missing from another locale's catalog (`tr.json` beside `catalog: catalog/en.json`) passed. A placeholder with no sample value is still looked for in the named catalog only.
- `check` replays a flow's `tutorial.yaml` on the flow (SPEC.md §7). The new rule `tutorial-mismatch`, which fails `--strict`, is given at the step where the tutorial no longer matches: its `flow` is another flow; its `scenario` names a variable or a value the flow does not have, or gives none for a variable that starts from any value; a step names a state, a node, an event, a variable of `then` or a value the graph does not have, or a `{word}` that is neither a sample value nor a node with visible text; or the replay stops at the step (`show` where the flow is in another state, `press` on a node that is not shown, is disabled or sends no event the state handles, `after` an event the state does not handle, `cut` to a state no reachable situation is in, `reveal` or `focus` a node the screen does not show, `end` where the flow is not, a `then` no case matches). A tutorial told on the diagram (`stage: diagram`) is replayed as SPEC.md §7 says, and one that points at a node stops. Before, `check` did not read tutorials: a tutorial that named a step, an event or a node its flow no longer had passed. A tutorial may also carry `samples` of its own, which `check` counts as sample values for `{word}`; SPEC.md does not describe that key yet.

- `check`: every graph under a folder, as GNU error lines or SARIF 2.1.0, with `--baseline`; exit 0, 1 or 2.
- `page`: a graph's page in words, with its guarantees, screens and diagram.
- `diff`: what a revision changes in a graph, in words, for a pull request.
