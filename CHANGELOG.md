# Changelog

While the version is 0.x, a release that can judge the same graphs differently (a new check, a stricter schema) bumps the minor; a fix that judges nothing differently bumps the patch.

## Unreleased

- `check` parses each file once however many graphs read it. Before, it parsed a flow's domain again for every flow that names it, and every flow again for every flow that starts another: on delurio's own 41 flows it took 12.7 s, of which more than half was parsing the same files again; it now takes 5.8 s. It judges nothing differently: the same graphs give the same findings, in text and in SARIF, as 0.8.0 gives.
- A graph that cannot be loaded is reported, and the other graphs are still checked. Before, a `ui.yaml` with no `catalog` stopped the whole check with a stack trace (`ERR_INVALID_ARG_TYPE`), and so did a catalog file that was not there (`ENOENT`), a catalog that was not JSON, a `flow.yaml` or `ui.yaml` that was not a map, a flow with no `states`, a state that was not a map, and a guard, an assertion or a `starts` value that did not parse. Each is now a `load` error (exit 1), in text and in SARIF. A `ui.yaml` with no `samples` or no `nodes` now loads (the `schema` rule still reports a missing `nodes`); before, one whose words had a placeholder stopped the check the same way.
- A `load` error is given at its place (SPEC.md §10): the file it is in and the line of what it is about, or the line and column a parser gave. Before, every load error but a YAML one was given at `flow.yaml:1:1`, and a YAML error of `ui.yaml` at its line but in `flow.yaml`. Now a transition to a state that does not exist is given at the transition; a node's unknown state at that item of its `in`, `unless` or `disabledIn`; an unknown `focus` state, a `checked` that cannot be read and a kit that cannot be read at their keys in `ui.yaml`; a missing or unreadable catalog at `catalog`; a catalog that is not JSON in the catalog, at the place the parser gave; a guard that does not parse, or names what is not a variable or a guard, at the transition that uses it (a named guard at its own line); an unknown effect at its transition; a non-exhaustive `always` at its `always`; an assertion at its `never`. Their messages and fingerprints are unchanged, so a baseline still knows them.
- A started flow is looked up among the graphs beside a flow without reading one that cannot be read: before, a neighbour's YAML error was also reported as a `load` error of every flow that starts another one.
- `--baseline`: a known error that keeps a graph from loading is printed as `error`, since it fails the run (exit 1) however often it was seen. Before, it was printed as `warning` while the run failed and the last line counted it as an error. The last line now counts each finding at the level it is printed at, so a known error printed as `warning` is counted as a warning. Exit codes are unchanged.
- New rules of `check`, which fail `--strict` (SPEC.md §2): `state-unreachable`, a state that no situation the flow starts in reaches, which the page already marked; and `state-no-way-out`, a state that is not an exit (`type: final`) and has no `on`, `always` or `invoke`, so that a flow that reaches it stops there without ending. Both are given at the state. Before, `initial: cart`, `cart: { on: { CONTINUE: done } }`, `pay: { by: human }` and `done: { type: final }` gave no error at all; now `pay` gives both. Transitions that no situation takes still fail nothing (#2).
- `catalog-key-missing` holds the catalog of every locale in `locales` (SPEC.md §4), at the key in `ui.yaml`, and a locale whose catalog file is not there is one error at `locales`. Before, only the catalog `ui.yaml` names was read, and a key missing from another locale's catalog (`tr.json` beside `catalog: catalog/en.json`) passed. A placeholder with no sample value is still looked for in the named catalog only.
- `check` replays a flow's `tutorial.yaml` on the flow (SPEC.md §7). The new rule `tutorial-mismatch`, which fails `--strict`, is given at the step where the tutorial no longer matches: its `flow` is another flow; its `scenario` names a variable or a value the flow does not have, or gives none for a variable that starts from any value; a step names a state, a node, an event, a variable of `then` or a value the graph does not have, or a `{word}` that is neither a sample value nor a node with visible text; or the replay stops at the step (`show` where the flow is in another state, `press` on a node that is not shown, is disabled or sends no event the state handles, `after` an event the state does not handle, `cut` to a state no reachable situation is in, `reveal` or `focus` a node the screen does not show, `end` where the flow is not, a `then` no case matches). A tutorial told on the diagram (`stage: diagram`) is replayed as SPEC.md §7 says, and one that points at a node stops. Before, `check` did not read tutorials: a tutorial that named a step, an event or a node its flow no longer had passed. A tutorial may also carry `samples` of its own, which `check` counts as sample values for `{word}`; SPEC.md does not describe that key yet.
- New warnings of `check`, which fail nothing (SPEC.md §5): `invoke-unknown`, a state that invokes an action the flow's domain does not have, a `failures.<state>.from` that names another action the domain does not have, or a flow whose named domain is not found beside it while its states invoke actions; and `refusal-unknown`, a failure class of a state that invokes an action listing a code that is not one of that action's `refusals`. A state that invokes an `external` or a `flow` is not held to the domain. They are warnings because whether these fail a run is still open (#5): a graph that lists transport failures (`network`, `5xx`) among a class's codes gets a warning for each.
- `check` looks a domain up once per run, however many flows name it; the `changes` rule and the warnings above share it.
- `examples/notes/edit`: a tutorial for the owner of a note, which `check` replays.
- The examples give the same findings as before: none.
- `examples/notes/kit`: a kit to start from (SPEC.md §8), which the screens of `examples/notes` are now drawn with (`kit: ../kit`). It has a template for every component of `ui.yaml`, and for the roles graphs most often give them: a `Button` or a `LinkButton` that is a link; a `List` that is a radio group, a group or a tab list; a `ListItem` that is a checkbox, a radio, a tab, a link or a button. It also draws `Checkbox`, `Radio` and `Select`, which `ui.yaml` does not name as components yet; a kit may give templates that no screen uses. Its colours, spaces, radius and type are design tokens in the W3C format, light and dark, each colour it draws text in at a contrast of at least 4.5:1 with its background, and its CSS takes every value from them. Nothing is judged differently: the examples give the same findings, and only the notes pages look different.
- README: how to write a product's own kit, starting from that one.
- `ui.yaml` may disable a control by what the context holds (SPEC.md §4): `disabledWhen: "<expression>"` beside `disabledIn`, which names states only. A Continue button disabled until a VAT number is typed is `disabledWhen: "not vatGiven"`, where typing it is an event whose effect sets `vatGiven`; one disabled until a box is ticked is `disabledWhen: "not accepted"`, beside the box's `checked: accepted`. A node is disabled where either says so, and a replay compares it in each situation it stops in. The graph cannot be loaded (exit 1) when the expression does not parse or names what is not a variable, a guard or `state`, as for `checked`. The page writes "disabled when …" on the node. Before, the `schema` rule refused the key; graphs without it are judged as before.
- A `returnsFocus` may give the focus back to whichever of several nodes opened its dialog (SPEC.md §4): `{ returnsFocus: [<dialog>, [<node>, ..]] }`, one of those listed, or `{ returnsFocus: [<dialog>, opener] }`, any node that opens it. A dialog that edits any of four fields gives the focus back to the Edit button that was pressed. `focusAfter` in `@delurio/cli/graph` takes the node pressed to open the dialog as a fourth argument, which a replay knows and the graph does not; without it, a list gives the one node of it the new state shows, and `opener`, or a list of which the new state shows several, gives null. `check` holds each node a list names, and each node that opens the dialog for `opener`, to `focus-not-shown`, and a dialog that no node opens fails it too. The `schema` rule refuses a node called `opener`. Before, the `schema` rule refused anything but one node in the second place; graphs that use one node are judged as before.
- `Checkbox`, `Radio` and `Select` are components (SPEC.md §4): each is named by its `text`, its label; a checkbox (role `checkbox` or `switch`) and a radio (role `radio`) say with `checked` whether they are checked; a select (role `combobox`) shows its `value` as the option chosen. The page draws them as a labelled box or `<select>`, and the expected accessibility tree, which a kit check holds a product's kit to, names each by its label. A kit's templates gain the flag `{?checked}` (SPEC.md §8). Before, the `schema` rule refused these components and the page had no renderer for them, so a graph wrote a checkbox as a `ListItem` with the role (which still works) or as a `TextField`, drawn as a text box. The examples' pages differ only by the CSS of the new box.
- `ui.yaml` may name its flow as its users know it, in every locale: `task: { key: <catalog key> }` (SPEC.md §4), such as "Edit a note", as `changes` gives the changes note. Rehber names the task by it in the page's language, where it borrowed the words of the flow's first button. New rule of `check`, which fails `--strict`: `task-locale`, a `task` key missing from, or empty in, the catalog of any locale. Graphs without `task` are judged as before.
- SPEC.md §4: while scripts do not run, an action of a page marked `script: actions` is not there, or is disabled and says why with an accessible description, such as that it needs JavaScript. A replay's `--no-js` walk checks each action such a state shows, and a dead button (visible, enabled, doing nothing) is a mismatch. The checker does not replay, so nothing is judged differently.
- SPEC.md §7: what a replay does with a binding. A walk reads every screen against the flow's catalog of its browser's language (`browser.locale`, or `--locale`), found by the whole tag and then by its language (`tr-TR` reads `catalog/tr.json`), and a locale with no catalog is refused; `--locale` may be given more than once, for walks in each language. `browser.ignoreHTTPSErrors: true` opens a page with a self-signed certificate. A walk keeps through a `havoc` the value its scenario's `given` gives a variable that starts from any value. Where several nodes send a step's event, the binding's `events.<EVENT>` says which is pressed. A navigation graph's binding may give `pages.<page>.samples`, the `:params` of one page's route, and its replay takes `--locale` too. The checker does not read bindings, so nothing is judged differently.

## 0.8.0 (2026-11-15)

- `ui.yaml` may say where the focus goes after a step, what a control holds, and which pages work without JavaScript (SPEC.md §4), so that a replay can check them on the app. Before, the `schema` rule refused all five keys.
  - `focus: { <state>: <node> }`: the node that has focus when the flow enters the state from another one, such as the alert a failed step shows on a page that stays open.
  - The edge `{ returnsFocus: [<dialog>, <node>] }`: when the dialog (a page node whose role is `dialog` or `alertdialog`) closes into a state that shows the node, the node has the focus, usually the one that opened it. This partly answers #3's focus return.
  - Where the focus goes is the first of these that applies: a dialog that closes and its `returnsFocus`, a page that opens and its `initialFocus` (a dialog's before the page's), then `focus`. `@delurio/cli/graph` exports this order as `focusAfter`.
  - A page opens however the browser got there, by a step inside the app or by loading the page anew, and its `initialFocus` holds in both.
  - `value` on a field: what it holds when it is shown, until someone types in it, as `{ key, params }`, `{ literal }` (`""` for an empty field) or `{ oneOf }`.
  - `checked` on a node whose role is `checkbox`, `menuitemcheckbox`, `menuitemradio`, `option`, `radio` or `switch`: whether it is checked, or selected, as an expression over the context, or `true` or `false`.
  - `script` on a page: how much of it works without JavaScript. `optional`: the page and its actions; a replay's second walk, with JavaScript off, checks it and takes its actions. `actions`: the page is drawn and read without JavaScript (rendered on the server) and only its actions need it; that walk checks what it shows but its actions, and ends there.
- New rules of `check`, which fail `--strict`: `focus-not-shown`, where `focus` gives the focus to a node its state does not show, or a `returnsFocus` to a node that no state the dialog closes into shows; and `returns-focus-not-dialog`, where a `returnsFocus` does not start at a dialog. The `schema` rule refuses `value` on a node that is not a field, `checked` on a node of another role, and `script` on a node that is not a page. The graph cannot be loaded (exit 1) when `focus` names a state the flow does not have, or when a `checked` expression does not parse or names something that is not a variable, a guard or `state`. A `value`'s catalog key and its samples are checked as a node's text is (`catalog-key-missing`, `sample-missing`). Graphs that use none of these keys are judged as before: delurio's 34 graphs give the same findings.
- `check` checks every folder it is given (`check graphs examples`), each graph and file once though one folder holds another. Before, it checked the first folder and left the others out without a word, and a path that was not a folder stopped it with a stack trace; now that path is refused with the usage, exit 1.
- `@delurio/cli/model` exports `cover` (#4). It gives event paths that together pass every reachable state (`states`) or take every reachable transition (`transitions`) of a flow, from the starts and through the steps that `explore` is given. Each path is a shortest way to what it is kept for, and has a stable id and the list of what it covers; the result also lists what no situation reaches. The same flow gives the same paths. `transitionsOf` names every transition as a step's `taken` does. A coverage report and a command that reads it are still #4.
- `@delurio/cli/graph` types the new keys (`UiNode.value`, `checked`, `script`, and now `repeat` and `source`; `Ui.focus` and `Ui.edges`, with `UiEdge`), and exports `shownIn`, `isDialog` and `CHECKABLE`.
- SPEC.md §7 describes what a binding and a replay add for this. A binding: a locator's `frame`; a scenario's `javaScript: false`; `as: <account>` on an action; `effects`; a node's `count`, how many elements its locator finds, on any node; a state's `call`, and its `as` and `before`, that person's screen and what is done on reaching it, for a step another person takes after arriving by a mailed link; and its `data`, read again after each `run`, a source whose file does not exist yet being allowed until a value of it is used. A scenario's `enter`: the way its walk comes in, by a navigation entry (`{ nav, bind, entry: <from>-><to> }`) or by another flow that starts this one (`{ flow, bind, given, event }`), after which the address it arrives at and the `initialFocus` of the first screen are checked and the flow's walk goes on. A replay: `--cover`, `--to`, `--no-js` and `--absent`. A navigation graph's binding: `nav:` in place of `flow:`; each persona signed in as the account named like it, or `personas.<persona>: { as, setup }` where one account stands for several personas and commands give it their facts; a `setup` run once; `frames` (`find`, `page`, `user`, `picker`), `pages` (`refusal`, `shows`, `skip`) and `entries.<from>-><to>[ <how or label key>]` (a locator, `skip`, `follow`), keyed as an entry is cited; and its replay, with `--persona`, `--page`, `--follow` and `--no-setup`. The checker does not read bindings, so nothing is judged differently.
- `examples/notes/restore`: its page is `script: actions`, drawn on the server while Restore needs JavaScript.
- `examples/notes/edit`: a page that works without JavaScript, with a field's value, a checkbox's state, the focus after saving, and a dialog that gives the focus back to the button that opened it. The notes domain gains `editNote`, a server function, and the field `pinned`.
- SPEC.md §7: a tutorial step may say how it comes out where an effect leaves it to chance (`havoc`): `then { <variable>: <value> }`. The step takes the case in which those variables have those values; without `then` it takes the model's first case. A tutorial can now go through an answer from outside (a host that lists the person's repositories) that the graph leaves open. The checker does not read tutorials, so nothing is judged differently.

## 0.7.0 (2026-11-12)

- An action may be a server function (SPEC.md §5): `serverFn: GET` or `serverFn: POST` in place of a route, for a call that the product's own pages make to its server through their framework, such as TanStack Start's `createServerFn` or React's server functions, at an address the framework gives it. It is not part of the product's HTTP API: it is no OpenAPI operation, its input is its `body`, and it has no `query` and no `operationId`. `GET` reads and changes nothing; `POST` may write. An address that the browser itself opens, such as a link in an e-mail or a sign-in callback, keeps its route even when a server function answers it. Before, such an action could only be written with a route, as an operation that others may call, or with none, as a step inside the service; the `schema` rule refused `serverFn`.
- New rule of `check`, which fails `--strict`: `server-fn-http`, a server function that also has a `route`, a `query` or an `operationId`. It is given at the `serverFn`, with a note at the other key, in whichever files of a split domain each is given. A method other than `GET` or `POST` is an error of the `schema` rule.
- The `changes` rule (SPEC.md §4) reads a server function's method as it reads a route's: a `POST` writes and a `GET` does not, even when it returns an entity. Graphs with no `serverFn` are judged as before.
- `page`: a flow's page lists what each of its steps calls, under "What each step calls": the action, and how it is called (an HTTP operation and its route, a server function and its method, or a step inside the service). It reads the flow's domain where the `changes` rule finds it; a flow whose domain is not found gets no list. The other parts of the examples' pages are unchanged.
- `examples/notes/restore`: a flow with a screen whose two actions are server functions, one `GET` and one `POST`, in the split notes domain.

## 0.6.1 (2026-11-11)

- `page`: in the flow's diagram, every state's group carries `data-state`, and every edge and its label `data-from` and `data-to`. One edge is drawn per pair of states, so a transition is found by its two states. A tool on top of the CLI can now find a state or a transition in the drawing, to move to it or link to it. The pages of the examples differ from 0.6.0's only by these attributes. Nothing is judged differently.
- `@delurio/cli/spine` exports `renderSpine`, which draws that diagram, with the states to draw as the story.
- SPEC.md §7: a tutorial may be told on the flow's diagram instead of its screens (`stage: diagram`), for a flow with no screens. `show` and `end` walk the flow to their state along its normal way, and every other event is given with `after`; an ending needs no card. The checker does not read tutorials, so nothing is judged differently.

## 0.6.0 (2026-11-10)

- A graph file with an anchor (`&name`), an alias (`*name`), a tag (`!name`) or a key that is a list or a map cannot be loaded (SPEC.md §1): `check` gives `load` and `schema` errors at its line, "unsupported YAML", and exits 1; `page`, `diff` and the other commands stop the same way. The yaml library resolves these in time far beyond a file's size. On a 40 KB file, maps used as keys kept it busy for more than 30 seconds, and aliases of an anchor that holds only aliases of an empty list for more than two minutes. Its alias limit does not catch these cases. Every reader of a graph file now looks for them first, in one pass that resolves nothing: such a file is refused in under a second. A value is written where it is used, and a key is a string. Of the graphs of delurio, Medaris and QAuth, only QAuth's has them: seven flows use anchors for a `response` they repeat.
- `@delurio/cli/yaml` exports that reader, `readYaml`, and `unsupported`, which names the first such place. A server that reads graphs it was sent should read them with it.
- New rule of `check`, which fails `--strict`: `source-missing`, a state of a captured flow (`status: captured`) that names no code (SPEC.md §9). An exit may leave it out, as the transition into it names the code. Flows that are not captured are judged as before.

## 0.5.3 (2026-11-06)

- `page`: the `flow.mmd` it writes now reads whole in Mermaid. Mermaid ends a statement at a `;`, even inside a transition's label, so a label with one lost its rest: those words were drawn as stray states, or, when a `-` or `{` came after the `;`, the diagram did not render at all ("Parse error on line …", QAuth's sign-in in an editor's preview). A `;` in a label is now written as a comma. A transition never taken and with no label of its own now carries "(never taken)" as its label: before, those two words were drawn as two more states. Of the 106 flow diagrams of QAuth, Medaris and delurio, 86 were drawn wrong (36 did not render, 50 had stray states) and none is now, in Mermaid 10.9 and 12.3; their 5 navigation diagrams were right before and are unchanged. `index.html` draws its own diagram and was not affected. Nothing is judged differently.

## 0.5.2 (2026-11-03)

- `page`: the flow's diagram opens fitted to a box as wide as the window, and moves like a design tool's canvas: drag it to move (the hand), Ctrl or ⌘ with the wheel, or a pinch, to zoom at the pointer, and the wheel alone to move it until its edge, after which the page scrolls on. Buttons and keys: − and + (zoom), the zoom level (click: 100%, Shift+0), Fit (Shift+1), Full window (F; Esc leaves it); arrows move it. A click that does not drag still opens a step's screen. Before, a large flow was shrunk into the page's column (QAuth's consent flow to 7%) or scrolled sideways at full size. Without scripts the page keeps the old diagram. Nothing is judged differently.

## 0.5.1 (2026-11-03)

- `check`, `diff` and `page` explore a large flow about four times faster and in a third of the memory, and judge every graph exactly as before: the same situations in the same order, the same shortest paths and the same findings. On QAuth's consent flow (5.4 million situations from 580,608 starts) `check` took 122 s and 2.9 GB, and now takes 34 s and 1 GB. A situation is kept as a number instead of a string; guards, assertions and effects are read once instead of at every situation; and an assertion is not tested in the states where the state alone rules it out.

## 0.5.0 (2026-11-01)

- A domain may be split across the files of its directory (SPEC.md §5): every `*.yaml` there that says `kind: domain`, read as one, `domain.yaml` first and then the others by name. Maps merge key by key at any depth, `policies` and `invariants` join, and any other value is given in one file only. `check` (the `schema` and `changes` rules), `diff` and `page` read the merged domain; before, a domain file not named `domain.yaml` was read by none of them.
- New rules of `check`, which fail `--strict`: `domain-twice`, a value or an invariant given in two files of a domain, at the second one's line with a note at the first; `domain-place`, a file whose id is not its directory's domain, or a domain whose files sit in two directories.
- `diff` heads the domain's changes "The API it calls (its domain)", and names every file of it it compared.
- An entity may carry `examples` (SPEC.md §5): records of it, each an object of its fields, as JSON Schema's own keyword. The `schema` rule refused it before.

## 0.4.0 (2026-11-01)

- An exit (`type: final`) may be named in snake_case, optionally followed by its cause: `signed_out`, `invalid_token.dpop_bound` (SPEC.md §1, Text). The `schema` rule accepts these names on exits only; every other state stays camelCase. `flow.mmd` writes such an id as `invalid_token__dpop_bound`, since Mermaid ids take no dot.

## 0.3.0 (2026-10-25)

- The modules a tool on top of delurio needs are importable, with their types: `@delurio/cli/graph`, `/model`, `/story`, `/wireframe`, `/kit`, `/edges`, `/html`, `/nav` and `/expr`. While the version is 0.x their API may change in any minor release; pin an exact version.
- SPEC.md §7: a video's AI disclosure is its first card, which says that the whole video is made with AI, in place of a label people see throughout.

## 0.2.0 (2026-10-25)

- JSON Schemas (2020-12) for `flow`, `ui`, `nav` (and `nav.extracted.yaml`), `domain` and `catalog` files, shipped in `schemas/`, for editors: completion, hover help from SPEC.md, and errors such as a typo in a key or a title cut short by a comma inside `{ }`.
- `page --watch` writes the pages again on every change under the folder; `page --serve [--port <n>]` also serves them on 127.0.0.1 and reloads the open page after each write, or says why a graph could not be loaded.
- `check` validates every graph file against its kind's schema: each place a file does not follow it is an error of the new rule `schema`, at its line and column, which fails `--strict` (exit 2) and works with `--baseline`.

## 0.1.1 (2026-10-25)

- `page` on a folder writes the page of every graph under it and `index.html` listing them, in one process.
- A folder that holds no graph gets one line instead of a stack trace; counts read in the singular when there is one.
- The README runs every command as `npx @delurio/cli`.

## 0.1.0 (2026-10-25)

- `check`: every graph under a folder, as GNU error lines or SARIF 2.1.0, with `--baseline`; exit 0, 1 or 2.
- `page`: a graph's page in words, with its guarantees, screens and diagram.
- `diff`: what a revision changes in a graph, in words, for a pull request.
